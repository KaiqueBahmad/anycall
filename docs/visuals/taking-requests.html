How a server takes a request

Taking a request off its queue and writing down who has it happen in one step, so a crash can never lose it. That step can't block, so clients ring a doorbell after every push.

    Why a script and a doorbell?

    Three ways a server could take a request. Only the last gets every property at once.

    BRPOP, then HSET

    • Blocks until a request arrives
    • Many queues on one connection
    • A gap: a crash between the two loses the request for good

    BLMOVE

    • Blocks and moves the request atomically
    • One queue per call: a server with 10 methods needs 10 blocked connections
    • Moves it into a list, not the id → server hash reaping reads

    Script + wake (AnyCall)

    • No gap: RPOP and HSET in one atomic script
    • Many queues, one connection for all of them
    • Can't block, so it needs the wake channel, with a 1s fallback

    What rings the doorbell

    The read loop always tries its queues first and only then waits. Any of these ends the wait:

    A wake message

    A client pushed a request for one of its methods. Which method doesn't matter; the loop tries all of them.

    A freed slot

    A worker finished, so a method that was at its concurrency limit can take again.

    A new subscription

    A method was registered. A request may have landed before the server was listening for it.

    1s with nothing

    The fallback. A missed wake costs at most this much, never a lost request.

    Latency with the wake: p50 about 2ms (Python) and 5ms (Java) against a local Redis 7.4. Without it, a request would wait for the server's next 1s look. The steps follow the rules in the code.
