How a server takes a request

A server moves a request off its queue and onto a list of its own in one blocking command, so a crash can never lose it, and an idle server is handed a new request the moment a client pushes it.

    Why BRPOPLPUSH?

    Three ways a server could take a request. The last one closes the gap and still blocks; what it gives up is reading every queue on one connection.

    BRPOP, then record the owner

    • Blocks until a request arrives
    • Many queues on one connection
    • A gap: a crash between the two loses the request for good

    Script + wake (before this)

    • No gap: RPOP and HSET in one atomic script
    • Many queues, one connection for all of them
    • Can't block: a pub/sub wake woke every idle server, each ran the script, plus a 1s fallback. 14 commands per call with 1 server, 24 with 6

    BRPOPLPUSH (AnyCall)

    • No gap: the move onto the processing list is one command
    • Blocks, and Redis wakes exactly one server per push. 9 commands per call, however many servers
    • One queue per call: one connection per method the server serves

    One loop per method

    Each method a server serves gets its own read loop, on its own connection, that repeats: wait for a free slot, then BRPOPLPUSH for up to 2s.

    A free slot first

    The loop asks for the next request only when its method is under its max_concurrency, so a busy method's requests stay in the queue and its backlog stays accurate.

    The server-wide cap

    Gates running, not taking: a request taken while every server slot is busy waits in the server, already on its processing list. Taking overshoots by at most one per method.

    The 2s block

    How long stop and unregister take to reach an idle loop, at one command per 2s while idle. It doesn't delay requests: a push ends the block at once.

    One connection each

    A blocked command holds its connection. It costs Redis no CPU, only memory, about 57 KB per connection.

    Measured with the Python library against a local Redis 6.0.16: 9 commands per call with 1, 3 or 6 servers, about 0.6–0.9ms per sequential call (Java about 2ms), and 2.5 commands/s per idle server. The steps follow the rules in the code.
